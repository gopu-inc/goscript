# Lexer and parser engineering for Goscript

Use this skill for tokens, lexical states, precedence, grammar productions, AST construction from grammar actions, and parse errors.

## Repository map

- The source scanner is `src/lexer/scanner.l` (Flex); the grammar is `src/parser/parser.y` (Bison).
- AST node definitions and constructors are in `src/ast/ast.h` and `src/ast/ast.c`.
- The root `scanner.c`, `parser.c`, and `parser.h` are generated by the root `Makefile`. Edit the sources, not generated copies, except when explicitly asked to inspect or patch generated output.
- `grammars/`, `syntaxes/`, and `vim/` provide editor syntax support. They are not the compiler parser and may need a coordinated update when syntax changes.

## Workflow

- Inspect neighboring lexical rules and grammar productions before changing syntax. Preserve aliases and established spellings unless the request changes them.
- For a new construct, follow the token's semantic value through Bison's `%union`/token declarations into the grammar action and AST constructor. Ensure the AST carries enough information for downstream execution.
- Check lexical rule ordering and start conditions in Flex, especially rules with overlapping prefixes or exclusive states such as decorator scanning.
- Review Bison precedence and associativity for operator changes; test representative nesting and ambiguous combinations rather than relying on a successful generation alone.
- Keep source locations and parse diagnostics useful. If the current parser cannot represent a desired diagnostic, make the smallest compatible improvement.
- Update editor grammars only when they track the changed user-facing syntax; do not treat editor highlighting as proof that the compiler accepts a construct.
- Validate with the repository's Flex/Bison build targets and focused language examples when implementation verification is requested.
